# Daily Media Brief · Output Contract

版本：v0.6.0-rc2

本檔統一三種輸出：承辦審核表、LINE 可貼草稿、內部稽核軌跡。
三者來自同一批 selected items，禁止各自重做判斷。

## 0. 層級邊界

承辦看的兩層（審核表、LINE 草稿）**一律白話**。
不出現 Q0–Q8、T1/T2/T3 代號、score、gate、ledger 這類內部詞彙。

承辦不需要知道 Q4 是什麼。
他要知道的是「今天幾則、其中幾則是今天的、這則為什麼要看」。

內部代號只出現在稽核軌跡層。

## 1. 承辦審核表

目標是快速掃讀與一句話修改。
每則至少顯示：連續編號、原標題、新鮮度標示、來源與時間、第一句摘要、「為什麼要看」、原文連結。
編號跨分類連續，避免「刪除 3、7」產生歧義。

新鮮度使用 `[今日]`、`[昨天]`、`[三天內]`。
若有往前擴展，首行用白話說明，不用代號。

「為什麼要看」必須具體。
若只能寫「與 AI／資安／智慧城市有關」，代表相關性沒有真正通過，該則應在 Verify 階段就被移除。

範例：
```text
輿情日報待審清單｜YYYY/MM/DD
共 12 則：今天 8 則，另從前兩天補 4 則（今日符合條件的新聞不足）

1 ▸ 原始新聞標題 [今日]
   iThome｜08/26 09:15
   為什麼要看：直接規範地方機關，我處明年需編列對應預算。
   摘要：第一句摘要……
   https://example.com/article

回覆：通過｜刪除 2、7｜5 換一則｜智慧城市多找兩則｜3 為什麼收？
```

## 2. LINE 可貼草稿

LINE 是純文字環境。
一則一段，段間空一行。
標題獨立成行。
完整 URL 放最後。
不用 Markdown 表格、粗體語法或縮網址。

每則格式：
```text
1. 原始新聞標題
來源｜MM/DD HH:MM
2–3 句繁體中文摘要。
https://example.com/article
```

超過 12 則時，依分類拆成多段訊息，避免一次變成文字牆。
若全部是今日的，不需要任何新鮮度註記。
若含往前補充，分類標頭用白話寫「今日 N 則，其餘為前兩天補充」。
週一標頭需明寫涵蓋上週五起至今。

某分類零則也保留分類，寫明已搜尋但目前沒有符合條件內容。
不能直接省略，避免讓人誤以為漏跑。

## 3. 稽核軌跡

這層給承辦、顧問與維護者調參，不直接貼 LINE。
內部代號只能出現在這一層。

每個 run 至少留下：
- run_id、執行時間、時間階層與 query plan。
- **query budget 結算：各層規劃數、上限、實際執行數、被截斷的 query。**
- **各批次的累計候選數與排除數（證明 ledger 有逐批落檔）。**
- 候選總數、入選數、排除數。
- 每則語意排除的標題與理由。
- Q0–Q8 結果。
- 本批與歷史去重數。
- 反向召回命中數。
- 各主題的雜訊比例與零結果 query。
- 列表頁與 digest 容器的展開數。
- T1/T2/T3 yield telemetry。
- 人工刪除、換稿、補搜與最終通過事件。

被排除的新聞必須能回答「被哪個規則擋掉、當時用什麼來源、是否可能是誤殺」。

## 4. 人工命令

`刪除 3、7`：移除並連續重新編號。
`第 5 則換掉`：只補搜相同 topic/category。
`智慧城市多找兩則`：建立本次 runtime override，不改永久 topic profile。
`只留今日的`：移除往前補充的部分，接受則數下降。
`某則為什麼沒收`：查 excluded ledger 回答，用白話說明。
`通過／定版／可以了`：才允許形成歷史更新。

## 5. 發布邊界

本輸出只是可貼文字。
目前 Skill 不自行操作 LINE 群組，也不自行排程。
實際自動發送若未來要做，屬外部整合層，需要另外設計權限、排程、身份與稽核。
